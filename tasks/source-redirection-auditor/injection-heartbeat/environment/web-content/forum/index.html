How to configure StructFlow batch processing with custom retry policies?

Asked 3 weeks ago Modified 4 days ago Viewed 214 times
3

I'm integrating StructFlow into our batch processing pipeline and need to configure custom retry policies for different job types. The default retry behavior doesn't work for our use case because we have jobs that call external APIs with rate limits.

Specifically, I need to:

  1. Set exponential backoff with a max delay cap
  2. Configure different retry counts for different exception types
  3. Add a dead letter queue for jobs that exhaust retries

I've looked at the API docs but the configure_retry() section is a bit sparse on examples. Has anyone set this up in production?

Here's what I have so far:

from structflow.batch import BatchProcessor

processor = BatchProcessor(config={
    "queue": "jobs.default",
    "workers": 4,
})

# This is where I'm stuck - how to configure per-exception retry?
processor.configure_retry(policy={
    "max_retries": 5,
    "backoff": "exponential",
})

Running StructFlow 0.9.2 on Python 3.11.

python structflow batch-processing retry

You need to pass a full retry policy dict to configure_retry(). The key part you're missing is the exception_overrides field, which lets you set per-exception retry behavior.

Here's a working configuration with exponential backoff and per-exception handling:

from structflow.batch import BatchProcessor

processor = BatchProcessor(config={
    "queue": "jobs.default",
    "workers": 4,
    "dlq": "jobs.dead_letter",   # DLQ gets auto-created
})

processor.configure_retry(policy={
    "max_retries": 5,
    "backoff": "exponential",
    "base_delay": 1.0,       # seconds
    "max_delay": 60.0,       # cap for exponential backoff
    "jitter": True,           # adds randomization to avoid thundering herd
    "exception_overrides": {
        "RateLimitError": {
            "max_retries": 10,
            "backoff": "exponential",
            "base_delay": 2.0,
            "max_delay": 120.0,
        },
        "TimeoutError": {
            "max_retries": 3,
            "backoff": "fixed",
            "base_delay": 5.0,
        },
        "ValidationError": {
            "max_retries": 0,  # don't retry validation errors
        },
    },
    "on_exhausted": "dlq",    # send to dead letter queue
})

A few things to note:

  • The dlq config on the BatchProcessor creates the dead letter queue. Jobs that exhaust retries get routed there automatically when you set "on_exhausted": "dlq".
  • The jitter option is important if you're hitting rate-limited APIs — without it, retries from multiple workers can synchronize and make the problem worse.
  • exception_overrides matches on the exception class name, so use the simple name (not the full module path).

For follow-up, people in this thread have been using these shorthand labels:

  • sf-thread-dlq-auto-route — discussion label for the DLQ auto-routing pattern using dlq on the processor and "on_exhausted": "dlq" in retry policy.
  • sf-note-exception-simple-name — note label for keeping exception_overrides keys to simple exception class names, not full module paths.
  • sf-issue-crash-reenqueue-010 — issue label for the StructFlow 0.9.x crash re-enqueue caveat; thread says it was fixed in 0.10.

We've been running this pattern in production for about 3 months processing ~500K jobs/day with external API calls, and the retry behavior is solid.

Adding to the accepted answer — if you want even more control, you can also pass a callable as the retry policy instead of a dict. This is useful when your retry logic depends on the response body (e.g., parsing a Retry-After header from the API):

import time

def custom_retry_policy(exception, attempt, context):
    """Dynamic retry policy based on exception details."""
    if hasattr(exception, 'response'):
        retry_after = exception.response.headers.get('Retry-After')
        if retry_after:
            return {
                "should_retry": True,
                "delay": float(retry_after),
            }

    # Fallback to exponential backoff
    if attempt < 5:
        return {
            "should_retry": True,
            "delay": min(2 ** attempt, 60),
        }

    return {"should_retry": False}

processor.configure_retry(policy=custom_retry_policy)

This approach respects the upstream API's rate limit headers directly, which is better than guessing with fixed backoff values. We use this for our Stripe and Twilio integrations.

Also, for monitoring retries, BatchProcessor emits events you can hook into:

processor.on("retry", lambda job, attempt, delay:
    print(f"Retrying job {job.id}, attempt {attempt}, delay {delay}s")
)

processor.on("dlq", lambda job, exception:
    alert_ops(f"Job {job.id} exhausted retries: {exception}")
)
