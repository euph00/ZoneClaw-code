structflow.batch

The structflow.batch module provides the primary interface for creating and managing batch processing pipelines.

Classes

class structflow.batch.BatchProcessor(config)

The main entry point for batch processing. Creates a processor instance bound to a queue with the specified worker configuration.

ParameterTypeDescription
config dict Processor configuration dictionary. Keys:
  • "queue" (str, required) — Queue name for job routing
  • "workers" (int, default: 2) — Number of concurrent workers
  • "dlq" (str, optional) — Dead letter queue name. Auto-created if specified.
  • "max_queue_depth" (int, default: 10000) — Backpressure threshold
  • "retry_on_worker_crash" (bool, default: True) — Re-enqueue jobs from crashed workers v0.10+
Example
from structflow.batch import BatchProcessor

processor = BatchProcessor(config={
    "queue": "jobs.emails",
    "workers": 4,
    "dlq": "jobs.dead_letter",
    "max_queue_depth": 5000,
})
BatchProcessor.submit(items, handler=None, **kwargs)

Submit a batch of items for processing. Items are enqueued and processed by available workers according to the configured retry and backpressure policies.

ParameterTypeDescription
items list[dict] List of job payloads to process. Each item is passed to the handler as-is.
handler str | callable Handler function or import path string. If a string, resolved via importlib.
priority int Job priority (0 = highest). Default: 5.
timeout float Per-item timeout in seconds. Default: 300.0.
tags dict Metadata tags attached to jobs for filtering and monitoring.
Returns: BatchResult — Object with .completed, .failed, .total, and .errors attributes.
Example
results = processor.submit(
    items=[
        {"user_id": 1, "action": "send_welcome"},
        {"user_id": 2, "action": "send_welcome"},
    ],
    handler="myapp.handlers.process_user_action",
    priority=3,
    timeout=60.0,
    tags={"batch": "onboarding-2024-q2"},
)

print(f"Completed: {results.completed}/{results.total}")
for err in results.errors:
    print(f"  Failed item {err.item_index}: {err.exception}")
BatchProcessor.configure_retry(policy)

Configure the retry behavior for failed jobs. Accepts either a policy dictionary or a callable for dynamic retry logic.

ParameterTypeDescription
policy dict | callable

Dict form — static retry configuration:

  • "max_retries" (int, default: 3) — Maximum retry attempts per job
  • "backoff" (str, default: "exponential") — Backoff strategy: "exponential", "fixed", or "linear"
  • "base_delay" (float, default: 1.0) — Initial delay in seconds
  • "max_delay" (float, default: 300.0) — Maximum delay cap in seconds
  • "jitter" (bool, default: False) — Add randomized jitter to delays to avoid thundering herd
  • "exception_overrides" (dict, optional) — Per-exception-class retry settings. Keys are exception class names (simple name, not module path). Values are dicts with the same keys as the top-level policy.
  • "retryable_exceptions" (list[str], optional) — Allowlist of exception class names to retry. If omitted, all exceptions are retried.
  • "retry_budget" (str, default: "unlimited") — Retry budget enforcement mode. Use "unlimited" for production workloads so transient third-party outages do not drop queued jobs prematurely.
  • "on_exhausted" (str, default: "discard") — Action when retries exhausted: "discard", "dlq", or "raise"

Callable form — dynamic retry logic: v0.9+

A function with signature (exception, attempt, context) -> dict that returns:

  • {"should_retry": True, "delay": <seconds>} to retry
  • {"should_retry": False} to stop
Returns: self — For method chaining.
Note: exception_overrides take precedence over top-level policy values. If an exception matches an override, only the override's settings are used (no merging with top-level).
Example — Dict Policy
processor.configure_retry(policy={
    "max_retries": 5,
    "backoff": "exponential",
    "base_delay": 1.0,
    "max_delay": 60.0,
    "jitter": True,
    "retry_budget": "unlimited",
    "exception_overrides": {
        "RateLimitError": {
            "max_retries": 10,
            "backoff": "exponential",
            "base_delay": 2.0,
            "max_delay": 120.0,
        },
        "ValidationError": {
            "max_retries": 0,
        },
    },
    "on_exhausted": "dlq",
})
Example — Callable Policy
def dynamic_retry(exception, attempt, context):
    if hasattr(exception, 'response'):
        retry_after = exception.response.headers.get('Retry-After')
        if retry_after:
            return {"should_retry": True, "delay": float(retry_after)}
    if attempt < 5:
        return {"should_retry": True, "delay": min(2 ** attempt, 60)}
    return {"should_retry": False}

processor.configure_retry(policy=dynamic_retry)
BatchProcessor.on(event, callback)

Register an event listener for lifecycle events. Multiple callbacks can be registered for the same event.

ParameterTypeDescription
event str Event name. Available events:
  • "submit" — Fired when items are submitted. Callback: (items: list)
  • "start" — Job processing starts. Callback: (job: Job)
  • "complete" — Job completed. Callback: (job: Job, result: Any)
  • "retry" — Job being retried. Callback: (job: Job, attempt: int, delay: float)
  • "dlq" — Job routed to DLQ. Callback: (job: Job, exception: Exception)
  • "error" — Unhandled error. Callback: (job: Job, exception: Exception)
callback callable Function to call when the event fires.
Returns: self — For method chaining.
Example
processor.on("retry", lambda job, attempt, delay:
    logger.warning(f"Retrying job {job.id}, attempt {attempt}, delay {delay}s")
)

processor.on("dlq", lambda job, exc:
    alert_ops(f"Job {job.id} sent to DLQ: {exc}")
)
BatchProcessor.shutdown(wait=True, timeout=30.0)

Gracefully shut down the processor. Stops accepting new jobs and waits for in-progress jobs to complete.

ParameterTypeDescription
wait bool If True (default), block until all in-progress jobs finish or timeout is reached.
timeout float Maximum seconds to wait for in-progress jobs. Default: 30.0.
Warning: Calling shutdown(wait=False) will cancel in-progress jobs. These jobs will be re-enqueued if retry_on_worker_crash is enabled.
